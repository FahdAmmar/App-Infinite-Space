# Testing and verification

How the project is tested, what the final verification proved, and what was never verified. Back to the [README](../README.md).

## Testing

`npm test` runs 994 unit tests in 85 files (default environment `node`; the 20 files that need a DOM declare `// @vitest-environment jsdom`) covering validation, search and sorting, copy naming, the storage adapters (corruption, backups, quota errors, canvas copy/delete, the hybrid adapter), the workspace store (including dashboard summaries), the node factory, the canvas store (selection, duplication, editing state, connections, groups, size limits, isolation between editors), undo/redo (steps, transactions, merging, limits, restoring groups), the canvas codec with hostile and damaged input, the autosave controller (debounce, maximum wait, failures and retry, stale writes, serialization of writes) under fake timers, the image cleanup safety rules, group and connection rules, URL and tag helpers (including hostile schemes such as `javascript:` and `data:`), image validation and intake, the image storage fallback, the object-URL cache, the saved UI preferences (theme, sort, background effect, with untrusted input), toast behavior, the geometry and smoothing helpers of the Three.js scene, and `cn()`. Phase 7 added tests for the error screens (React rendered with `createRoot` and `act` through `src/test-utils/render.ts`, no test library), the export file format and import with hostile files (wrong format or version, `javascript:` links, invalid or oversized images, `__proto__` keys, ids pointing at another workspace's images), the rollback paths when saving fails, backup listing and restore, the storage estimate, the pausable autosave controller, the tab channel (with a fake channel), and the Data & backup components. Phase 8 added tests for reattaching a connection (duplicates, groups, undo), the copy and paste rules (group members, detaching a card from an uncopied group, centering at the pointer, remapped connections, size limits), aligning and distributing (including cards inside groups), moving several cards as one undo step, the snap preference, the search rules (case, accents, Arabic marks, `#tag`, ordering, regular-expression characters), the find bar's keys and counter, and the layer ordering (groups stay behind, saved order). Phase 12 added tests for the slide ordering and stepping, the template catalog and every template's cards (limits, connections, no overlaps, notes inside frames, passing the import validator without loss, a view that fits the screen) and the template picker in the create dialog. Phase 11 added tests for the connected-card planner (position, side, handles), the text-paste planner (links, paragraphs, hostile addresses, limits, grid layout, a huge paste), the command search ranking and the palette view (filtering, arrow keys, `aria-activedescendant`), the image compression decisions (what to recompress, animation detection, accepting only a clearly smaller WebP) and the intake fallbacks when compression fails, the saved compression preference, the tag filter (case, groups, counts, dimmed copies reused by identity), the rejected-drop explanations, the toolbar placement maths, and the toast lifetime. Phases 15 and 16 added tests for the focus branch (upstream and downstream, siblings left out, cycles, a 5,000-card chain), the right-click menu model and view (items per target, selection rules, keyboard, screen-edge flipping), card links (encoding and hostile values), the outline order and labels (Arabic included), the semantic-zoom scale, the getting-started progress, the theme modes and the saved preferences (unknown values ignored), the diagnostics text (no workspace id), the read-only HTML page (escaping a `</script>` title and card text, only web links, only raster data URIs, missing cards dropped) and its export service, the cross-workspace card search, and snippets (images left out, damaged or oversized stored data dropped).

The user-facing flows were verified in Chromium against the production build.

- **Phase 3:** [`e2e/phase3_flows.py`](../e2e/phase3_flows.py) runs 43 checks: connecting by dragging, with the Connect tool, and with Connect to…, duplicate and invalid connections, editing a connection (dashed, arrows, label, gradient), adding, rejecting, previewing, captioning, replacing, resizing, and deleting images (IndexedDB round trip and aspect ratio), link addresses (normalization, `javascript:` rejection), groups (capture, move, release, delete keeps cards), drag-and-drop and paste of images, deleting and duplicating, light theme, and no console errors. Run it by hand as described at the top of the file.
- **Phase 4:** [`e2e/phase4_persistence.py`](../e2e/phase4_persistence.py) runs 43 checks: saving and restoring every kind of card, connection, group membership, image bytes, and the pan/zoom after a reload; undo/redo by keyboard and buttons (a whole drag, a delete with its connection, a group move, creation plus first text, quick arrow-key nudges); the saved state matching the undone state; leaving the editor right after an edit; dashboard counts and previews; duplicating and deleting workspaces; a simulated storage failure with Retry; the leave-confirmation; unreadable and partly damaged saved data (with a `javascript:` link address planted in storage); and the image cleanup (an unused old image removed, a used one kept). It takes about a minute because the cleanup starts 8 s after load.
- **Phase 5:** [`e2e/phase5_polish.py`](../e2e/phase5_polish.py) runs 66 checks in four browser contexts (desktop, reduced motion, direct editor load, touch): the Three.js effect (starts with exactly one canvas, takes no pointer input, really paints pixels, turns off and on and remembers the choice, stops drawing while the tab is hidden and resumes, keeps running across a theme switch, is never created or downloaded for the editor), reduced motion (no canvas, disabled toggle, no entrance animation, no beam), Magic Card and Border Beam, GSAP (chrome fades in on entry and leaves no inline styles; the dock stays exactly centered; a duplicated card enters), keyboard use (skip link, reaching and moving a card, the focus indicator of every Tab stop on the dashboard and in the editor), layout at 390, 768, 1024, and 1440 px (no overflow, nothing overlapping, panel inside the screen), 44 px touch targets, and axe-core. Pillow is needed for the pixel comparison, and axe runs only if `AXE_PATH` points at `axe.min.js` (`npm i axe-core` somewhere outside this project).
- **Phase 6:** [`e2e/acceptance.py`](../e2e/acceptance.py) walks the specification's Definition of Done as one continuous user journey (25 checks, including the light theme, a phone, and a tablet), and [`e2e/phase6_stress.py`](../e2e/phase6_stress.py) is the load test described under Verification. The whole run takes about five minutes, so the stress script can be split with `SIZES`, `SKIP_UPLOADS`, and `ONLY_UPLOADS`.
- **Deployment:** `npm run deploy:check` (after `npm run build`) runs 47 checks on `vercel.json` and `dist/` (including the manifest, icons, and the service worker's precache list): the single-page fallback and that missing assets stay 404, caching, security headers, the inline-script hash in the CSP, no `eval`, local fonts, and no secrets. It was also run against four deliberately broken configurations and failed each time. It does not use a browser or Vercel.
- **Phase 7:** [`e2e/phase7_data_safety.py`](../e2e/phase7_data_safety.py) runs 20 checks: export (a real download), import, a rejected foreign file, restoring a recovery copy, the tab-conflict banner (inside the screen and clear of the top bar on a desktop and a phone), and the error screen when the editor download fails. It passed five runs in a row; the first run found one ambiguous selector, and two checks needed to wait for the asynchronous recovery list.
- **Phase 8:** [`e2e/phase8_productivity.py`](../e2e/phase8_productivity.py) runs 46 checks: reattaching a connection (one undo step, a refused self-connection with its message), copy, cut, paste, undo and redo of a paste (also into another workspace), layers, align and distribute, snap to the grid, find (counter, stepping, panning to a match), and a 390 px phone (zoom toolbar, properties panel, action bar, minimap, empty-canvas hint). Its first runs failed on five real defects, listed under Phone and layout fixes in [FEATURES.md](FEATURES.md), all fixed.
- **Phase 15:** [`e2e/phase15_ux.py`](../e2e/phase15_ux.py) runs 28 checks at 1440 px and 390 px: the dashboard row, the getting-started list ticking by itself and staying dismissed after a reload, the palette button, high contrast (applied before first paint), the system theme following a changing operating-system setting, the one-row phone toolbar, touch wording, and a long-press opening the menu.
- **Phase 16:** [`e2e/phase16_navigation.py`](../e2e/phase16_navigation.py) (43 checks: focus branch, right-click menu on the canvas, a card and a connection, deep links including a missing card and a hostile parameter, outline, semantic zoom), [`e2e/phase16_share.py`](../e2e/phase16_share.py) (24 checks: the exported page opened from `file://` with a hostile card, no network request, zoom, pan, fit, theme; the workspace menu; search inside workspaces in Arabic and English) and [`e2e/phase16_snippets.py`](../e2e/phase16_snippets.py) (12 checks: save in one workspace, insert in another, again with new ids, survive a reload, damaged storage). - **Phones and long text:** [`e2e/phone_text_flows.py`](../e2e/phone_text_flows.py) runs 15 checks with touch emulation at 390 px and 320 px and a mouse at 1440 px: a card with a 60-character Latin or Arabic name fits the screen and the page does not grow wider than the phone; every text field is at least 16px on touch (create dialog, find bar, command palette, title edit, card editor) and keeps its compact size with a mouse; the decorative 3D scene is not downloaded on a phone and still is on desktop; the beginning of a long Arabic name stays visible in a card and in the editor title, which has at least 60 px of text room. Run against the project as it was before these fixes, 10 of the 15 checks failed.
- **Phase 17:** [`e2e/phase17_ux.py`](../e2e/phase17_ux.py) (21 checks: the Create button visible without scrolling at 1440×900 and 390×844, the empty state and one-click templates, safe areas simulated by overriding `--safe-*`, the phone "+" menu, and offline reload of the editor and dashboard through the service worker) and [`e2e/phase17_backup.py`](../e2e/phase17_backup.py) (19 checks: the reminder and its snooze, folder backup simulated with the browser's private file system, overwrite on re-backup, disconnect, and the download fallback). - **Phase 18:** [`e2e/phase18_cards.py`](../e2e/phase18_cards.py) (56 checks: the status ring cycling with undo and redo, locking (a locked card keeps its place, survives Delete with a message, and unlocks), the checklist (add, tick, progress, title, remove, undo), shapes (text, kind change), Markdown rendering including hostile HTML, the video card (no request to YouTube before play, a refused non-YouTube address, a sandboxed `youtube-nocookie` player), the links panel, tree and column layouts as one undo step, and everything surviving a reload).
- **Running everything:** `npm run e2e` builds, starts the preview, and runs every script in `e2e/` in turn. The older scripts go through `e2e/_common.py`, which blocks the service worker (it would hide requests from `route()`) and fixes the reported core count. `npm run size:check` enforces the bundle budgets after a build.
- **Load test:** `e2e/phase6_stress.py` passes all 51 checks. Two checks used to fail (the dashboard item count after undo at 1,500 and 3,000 items). The cause was the test, not the app: its edit step clicked a fixed point that lands on an existing card once the screen is full, so no field took the focus, the typed letters ran as keyboard shortcuts, and a stray card was created that one undo could not remove. The step now creates the card with the `n` shortcut, checks that the focus is inside the new card's field and that the text lands in a sticky, and undoes one or two steps until the card is gone.
- **Phase 12:** [`e2e/phase12_flows.py`](../e2e/phase12_flows.py) runs 45 checks: presentation mode (starting, reading order, every navigation key, no wrap-around, blocked editing shortcuts, a slide that cannot be dragged, restoring the previous view, starting on the selected group, the palette command and the buttons) and the template gallery (the picker, name suggestions, a Kanban board of three columns and five notes, notes that move with their column, survival across a reload, the mind map, SWOT, roadmap and retrospective, name collisions, and Blank still empty).
- **Phase 11:** [`e2e/quickwins_flows.py`](../e2e/quickwins_flows.py) runs 50 checks: dragging a dot onto empty canvas, pasting a link and paragraphs (and a dangerous address staying text), the command palette (opening, running commands, focus after *Find*, switching workspace), image compression with real files the script generates itself with Pillow (a 3600×2400 JPEG of about 4 MB, a small PNG, an animated GIF), and the tag filter. - **Phases 1 and 2:** earlier Playwright scripts (50 checks for the dashboard, 76 for the canvas) were run at the time but **are not in this repository**.
- **Accessibility:** axe-core (WCAG 2.0/2.1 A and AA) reported no violations in seven Phase 3 states (link editor open, connection selected, image selected, image preview dialog, group selected, in both themes) six Phase 4 states (saved, save error with Retry in both themes, undo enabled, and a populated dashboard card in both themes), and Phase 5 states (the dashboard with the effect in both themes, and the editor with the properties panel open at four widths). Automated checks find only part of the possible problems; the keyboard checks above are automated, but nobody has used the app with a screen reader, so announcements (the save status, card moves) are untested in practice.
- There is **no automated browser test in CI** yet. It is listed under Future additions in the [README](../README.md).

## Verification

Phase 6 ran the application against the specification's Definition of Done, then against large workspaces and many large images. Everything below was run on the production build in headless Chromium inside a sandbox with software rendering and no GPU; absolute numbers will be better on a real machine, and each figure is a single run, so expect noise (for example, the 3,000-item row's save and undo times are higher than the 4,940-item row's). What matters is the shape: costs grow roughly linearly with the item count and nothing collapses.

### Load test

Generated canvases were written straight into IndexedDB (so reading and validating them is part of the test), mixing notes, text, links, images, groups, and connections. "DOM cards" is how many cards exist in the page at normal zoom, and at "fit all" (everything on screen, the worst case). Frame times are the 95th percentile (p95) of a synthetic pan with the mouse; at 60 fps a frame is 16.7 ms.

| Items | Connections | Open | DOM cards (normal / fit all) | Pan p95 | Drag p95 | Pan p95 at fit all | Save | Undo | JS heap |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 55 | 39 | 0.4 s | 20 / 55 | 33 ms | 67 ms | 67 ms | 0.8 s | 0.05 s | 22 MB |
| 505 | 433 | 0.9 s | 20 / 505 | 33 ms | 67 ms | 100 ms | 0.2 s | 0.2 s | 40 MB |
| 1,515 | 1,317 | 1.9 s | 20 / 1,479 | 50 ms | 67 ms | 350 ms | 1.1 s | 0.6 s | 132 MB |
| 3,035 | 2,653 | 2.8 s | 20 / 1,836 | 33 ms | 33 ms | 150 ms | 3.3 s | 2.9 s | 84 MB |
| 5,000 (the limit) | 4,387 | 4.3 s | 20 / 1,954 | 50 ms | 67 ms | 450 ms | n/a | 1.2 s | 120 MB |

- **Only visible cards are rendered**, so normal panning and dragging stay near the display's frame time even at 5,000 items. Zoomed all the way out with thousands of cards on screen, every card is in the page and panning is slower (up to a few hundred ms per frame here). That is the known weak spot; there is no level-of-detail mode.
- **The minimap was the biggest per-frame cost** (10,000 items: pan average 198 ms with it, 90 ms without), which is why it starts hidden above 1,500 items.
- **Why the limit is 5,000.** A canvas of 10,000 items was also tried: it opened in about 7 to 15 s and panned at roughly 200 ms per frame here, so the limit was set at the largest size that stayed comfortable instead of allowing it. At the limit, the 5,001st card is refused with a message (checked).
- **A real bug found by this test and fixed:** the previous limit applied only when reading a canvas, so a canvas could grow past it and silently lose items on the next open. The limit is now enforced at creation as well. The test also led to replacing a quadratic scan in the undo history with a linear one.
- **Uploads.** Twelve images of about 2.4 MB each were added in 1.5 s, all decoded, and all survived a reload. A file over 10 MB, an image over 40 megapixels (7000×6000), a thirteenth and fourteenth file, a text file, and a corrupt `.png` were each refused with a readable message and without breaking the canvas.

### What was not verified

Safari, Firefox, real GPUs, real touch hardware, real screen readers, long-running sessions (memory over hours), two real tabs on the same workspace (the logic is unit-tested with a fake channel), the Phase 7 screens in a browser, and browsers with IndexedDB blocked (the fallback code is unit-tested, not exercised in a browser). Nothing here is a substitute for using the app on your own devices.
